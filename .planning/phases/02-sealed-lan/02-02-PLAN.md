<objective>
Unit provisioning. Today any two phones running OffMesh link, and contacts are 16-hex IDs
typed by hand. After this plan a phone belongs to one unit: a 32-byte unit secret plus a
roster of members (static X25519 public key and a short name). One phone creates the unit,
adds the others by their identity code, and shares the unit code as a QR code or text; the
others import it. Contacts are the roster members.

Output: a pure-Dart roster codec with identity codes and fingerprints, a store over
SecretStore, provisioning in ChatController, a provisioning screen, and member fingerprints
on the home screen.
</objective>

<scope>
In: REQ-13 (storage and refusing to link when unprovisioned), REQ-14 (QR and text code,
Android camera scan, Windows paste), REQ-17 (fingerprints).
Out: sealing LAN frames, sealed beacon and hello, rotating IDs on the wire, and building
RosterResolver from `UnitKeys.idKey` (plan 02-03; no RosterResolver call site exists in
`lib` yet). Delivery marks (02-04). Rekey and revocation (not designed).

Known limits:
- The v1 roster is unsigned. Whoever holds the unit secret is trusted and can add members
  or hand out a changed roster. Operators compare fingerprints by eye to catch a wrong key.
- The unit code carries the unit secret in clear. Show it only to unit members, in person.
- Re-import replaces the whole unit; there is no merge. To add a member, the phone that
  added them shares the new code and every other member re-imports it.
- Epoch key chain not adopted in v1: the seal key is `UnitKeys.sealKey` for the unit's
  lifetime.
</scope>

<format>
Unit (binary, then text `OFFM-UNIT1:` + base64url with padding):
`version u8 (=1) | unit secret 32 B | member count u8 (1..32) | members`,
each member `public key 32 B | name length u8 (1..16) | name UTF-8`.
Strict: unknown version, truncation at any field, trailing bytes, zero or more than 32
members, empty or over-long name, invalid UTF-8 and duplicate public keys are all
rejected with RosterFormatException (message never contains key bytes).
32 members with 16-byte names encode to 1,602 bytes, 2,147 text characters: fits one QR
code at error-correction level M (byte capacity 2,331), tested.

Identity code: `OFFM-ID1:` + base64url(public key 32 B | name UTF-8 1..16 B).

Fingerprint: SHA-256(public key), first 16 bytes, as 8 groups of 4 hex digits.

Text input is trimmed; base64url padding is optional on input.
</format>

<task type="auto">
  <name>Task 2: Unit store</name>
  <description>
    `UnitStore.load/save/generateSecret` over SecretStore key `unit.roster.v1`. One key keeps
    secret and roster atomic, so a re-import never leaves a new secret with an old roster.
    Absent → null (unprovisioned). Present but malformed or not base64 → UnitStoreException;
    the controller stays unprovisioned (no LAN) and shows the error on the provisioning
    screen. The damaged value is not overwritten until the operator joins a unit again.
  </description>
</task>

<task type="auto">
  <name>Task 3: Controller provisioning</name>
  <description>
    ChatController takes the SecretStore and the loaded unit. `createUnit(name)`,
    `addMember(identityCode)`, `importUnit(unitCode)`, `unitCode`, `identityCode(name)`,
    `members` with names and fingerprints (computed when the roster loads). Create and join
    save first, then start LanManager. `connect` refuses while unprovisioned. Contacts are
    the roster members except this phone; messages from senders outside the roster are
    dropped. The paste-16-hex add-contact path is removed (members need public keys).
  </description>
</task>

<task type="auto">
